I've spent more time than I expected on one word. In Spanish the literal translation of sandbox is «caja de arena», a sandpit, and I went back and forth on whether to use it. I kept «sandbox», but the sandpit stuck with me, because it explains very well what a sandbox is. And also what it isn't.

A sandpit with walls

A sandbox is a closed space where an AI agent works without being able to touch what's outside it: the rest of your folders, your keys, the internet. Like a sandpit in a park: the sand stays inside because there are walls. For people who code it's nothing new. For people starting out with agents, it's a word that hardly ever shows up on screen. The install usually asks you which model you want to use, not where the agent will be able to work.

And that question matters, because an agent works with your permissions. Whatever you can open, it can too: the .env of a project you no longer remember, the cloud credentials left in your home folder, your tax return documents.

Almost all have one, almost none turn it on

On 15 November we went through the official documentation of the nine agents RosmarOps evaluates, one by one, looking for three things: whether they have a sandbox, whether it's on by default and whether it cuts off the network.

And the result is almost always the same: they have one, but it's off.

Codex is the exception. The rest have one, but you almost always have to go and find it:

  • Codex: on by default in Windows, macOS and Linux, with the network cut off until you decide to open it.
  • Cursor: on by default, but only on macOS and Linux.
  • GitHub Copilot in VS Code, Gemini CLI and Antigravity CLI: they have one on Windows, macOS and Linux, off by default. On Linux, Gemini CLI's only works with a container.
  • Claude Code and Grok Build: only on macOS and Linux, off by default.
  • Hermes Agent: isolated if you set it to work inside a container.
  • Cline: doesn't mention it.

Claude Code was the first one I looked at, because it's the agent I build RosmarOps with every day. Its documentation leaves no room for doubt: the sandbox is off by default. And on Windows it simply doesn't exist: it runs commands without one.

Turning it on isn't enough

My first draft of this article said that a sandbox «doesn't make an agent harmless: it limits what it could touch». That's true, but when I reread it I realised it fell short. The most important part was missing.

In many agents, the sandbox limits what the agent writes and where it connects, but not what it reads. The agent can still read your key. And if the network is open, that key can get out.

And the network isn't always closed. In GitHub Copilot, with the sandbox on, the network stays open by default. Cursor lets through a list of domains, including those of the package managers. In Grok Build, on macOS, its own documentation warns that the network cut-off does nothing. That's why the network cut has its own line in the table: having a sandbox and cutting off the network are two different things.

And Claude Code has its own small print. In Claude Code, the sandbox only covers the commands the agent runs in the terminal. Its documentation says that the tools it uses to read and edit files, its MCP servers and its hooks run outside it.

Back to the sandpit: turning on the sandbox is putting the walls up. But you have to check where they're still open.

When the maker says two things

Reading official documentation has a catch: it doesn't always say the same thing everywhere.

Cline's documentation says every action asks for your approval. Its code, freshly installed, approves reading and editing files without asking. And on 12 November, according to its changelog, Antigravity CLI started up in Auto mode, where another AI model decides which commands run without asking you. Its documentation still says it asks you first.

I don't know which of the two versions holds on your computer. So in the table I put a dash and show both quotes. I'd rather do that than pick one and get it wrong. What couldn't be read, or couldn't be confirmed, doesn't count as clean.

Where all this lives

All of the above is in a table, Which AI coding agents have a sandbox, agent by agent and system by system, with a link to each maker's page and the date we read it. It's also in the Observatory, which is now organised by company and shows four protections for each agent: sandbox, read-only mode, whether it asks first and network cut.

With that data, the Observatory says which agents to start with if you don't know them. Today they are Codex, because its sandbox and network cut are on by default, and GitHub Copilot in VS Code, because it has a read-only mode and asks you before running commands. The criterion is written down in the methodology and it's the same for everyone. No one pays to appear, or to be recommended.

RosmarOps doesn't set up a sandbox for you or turn on your agent's. It reads the configuration you have and tells you what each agent could touch. For Claude Code, Cursor, Codex and Grok Build it also reads their sandbox settings: if you turn it on, at the next review you see how its score changes.

Before you give it your folder

If you're going to try an agent you don't know, don't open it in your home folder. And creating an empty folder and opening it there isn't enough: most agents can read your whole home folder anyway. Turn on its sandbox if it has one, use a profile that stops it reading outside the project or, if there's no other way, open it from another user account on the computer. Then run RosmarOps in that same environment and see what it could touch.
